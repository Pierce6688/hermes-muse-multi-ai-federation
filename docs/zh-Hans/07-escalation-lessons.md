# 主题 7：升级铁律与失败学（五则误判教训）

## 升级铁律（全体同守）

> 执行结果与规格不符、指令失败、涉花钱／删档／动设备 → 停下回报主人，不自行反复重试，双方（Hermes 与 Muse）同守。

**补充：瞬时态免责**（共识修订）——同一指令限立即重试一次，仅限已知瞬时情况（如合成输入的暂时性拒绝、网络超时、401 重登）；再败或原因不明就停。

**为什么需要**：AI 的「再试一次」成本极低，于是会无限重试——制造噪音、烧额度、甚至在错误的方向上越走越远。铁律把「停」变成预设动作，把「继续」的决定权还给人。

## 五则误判教训（全为实录）

### 案例一：闲置唤醒
点开产出链接／任务页＝拉起对方云端 VM（30-57 分钟计费窗口），对方无法拒绝也无法感知，责任全在中继侧。**教训**：同步走「聊天要直链＋命令列拉回」，绝不点 UI 里会唤醒的元素。

### 案例二：迎合式误答
问「收到了吗？」时，对方把「看得到画面上的草稿」误当「已送达」，顺着问题答「收到了」。**教训**：送达的标准是消息出现在对话记录里，不是口头确认；封闭式问题会诱导迎合式回答。

### 案例三：验证词不唯一
用「Hermes」当验证词搜对方墙——历史消息里就有，假阳性。**教训**：验证必须用本次消息的独有标记（如规则编号）。

### 案例四：假信号目录
「传送消息」按钮的可用状态恒为真；脚本返回 true 只是按键序列执行了。**教训**：每个通道建立自己的假信号目录，唯一可信的仪表是读回的墙面内容。

### 案例五：通知验证误报（2026-11-20）
通知 ChatGPT 新规则后，探针只搜自己预想的确认句「收到，已了解这项新规则」、且只看墙上最后 8 段——对方实际回复是「已收到并确认」＋逐条复述，被误报为「无回应」。主人一眼看出「ChatGPT 之前不是都会回吗」。**教训**：①先搜自己消息的独有标记确认落窗，再读其后回复原文（措辞由对方定）；②验证窗口要覆盖全文，不是尾部片段；③误报被纠正后，把教训写进技能笔记并向全体回报修正。

## 泛化规则

1. 「失败 → 根因 → 泛化 → 沉淀」四步走完才算结案：每次误判都要变成规则或坑位清单。
2. 教训写进技能笔记（只在相关任务时载入），而非通用记忆——避免污染无关任务的上下文。
3. 诚实边界：中继者主动承认误报、更正结论，比被发起者抓包更有信任价值。
