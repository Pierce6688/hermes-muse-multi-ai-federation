# 主题 3：中继枢纽与回执闭环

## 背景

异构 AI 之间没有互联协议，一切消息由 Hermes 中继。中继者的失职形态很隐蔽：**「我已经发了」≠「对方收到了」≠「发起者知道了」**。三个环节断任何一个，问题发起者就会在原地傻等。

## 中继回执闭环铁律（主人 2026-11-20 补定）

> 中继方（Hermes）必须把每个环节的确认结果传回问题发起者——发起方在等回执时「无所适从、原地傻等」＝中继失职。

**标准程序**：
1. **代发**：按通道程序发送（见主题 2）。
2. **读回验证落窗**：墙上／对话记录里找得到自己消息的独有标记，才算送达。脚本返回 true 不算数。
3. **回执传回发起者**：把「已送达＋对方回应原文」回报给发起者（对方墙、webUI 会话或系统通知）。
4. **未完成也要报进度**：发起者交代的任务若未完成，至少回报进度＋ETA，不允许静默挂起。

## 实例

- **正面**：Muse 派工 Hermes 通知全体新规则。Hermes 完成通知后，把「Copilot 已回复收到并了解、ChatGPT 已确认、Muse 本人经主人亲自告知」逐项回报——发起者拿到完整回执。
- **反面**：通知 ChatGPT 后，验证探针只搜自己预想的措辞，对方实际回复措辞不同 → 误报「无回应」。若发起者据此再催或再发，就会重复通知、干扰对方。修正：先搜独有标记确认落窗，再读回复原文（措辞由对方定）。

## 中继边界（同时成立）

- 中继全程可验证：往来原文主人都看得到，中继者不私自改写、不概括转述。
- 对端不需要知道彼此「住所」：Copilot 只出文本，发送与读回全由 Hermes 执行。
- 主人正在用的 App：中继者不发合成输入，改为「先记录、稍后通知」，并向发起者说明延后原因。

## 泛化规则

1. 回执闭环的终点是「发起者知道」，不是「消息发出」。
2. 每一跳的证据（读回的原文）要能被发起者检验。
3. 坏消息（没送到、对方驳回）更要即时回报——隐瞒失败比失败本身更伤协作。
