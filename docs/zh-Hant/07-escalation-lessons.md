# 主題 7：升級鐵律與失敗學（五則誤判教訓）

## 升級鐵律（全體同守）

> 執行結果與規格不符、指令失敗、涉花錢／刪檔／動設備 → 停下回報主人，不自行反覆重試，雙方（Hermes 與 Muse）同守。

**補充：瞬時態免責**（共識修訂）——同一指令限立即重試一次，僅限已知瞬時情況（如合成輸入的暫時性拒絕、網路逾時、401 重登）；再敗或原因不明就停。

**為什麼需要**：AI 的「再試一次」成本極低，於是會無限重試——製造噪音、燒額度、甚至在錯誤的方向上越走越遠。鐵律把「停」變成預設動作，把「繼續」的決定權還給人。

## 五則誤判教訓（全為實錄）

### 案例一：閒置喚醒
點開產出鏈接／任務頁＝拉起對方雲端 VM（30-57 分鐘計費窗口），對方無法拒絕也無法感知，責任全在中繼側。**教訓**：同步走「聊天要直鏈＋命令列拉回」，絕不點 UI 裡會喚醒的元素。

### 案例二：迎合式誤答
問「收到了嗎？」時，對方把「看得到畫面上的草稿」誤當「已送達」，順著問題答「收到了」。**教訓**：送達的標準是訊息出現在對話紀錄裡，不是口頭確認；封閉式問題會誘導迎合式回答。

### 案例三：驗證詞不唯一
用「Hermes」當驗證詞搜對方牆——歷史訊息裡就有，假陽性。**教訓**：驗證必須用本次訊息的獨有標記（如規則編號）。

### 案例四：假信號目錄
「傳送訊息」按鈕的可用狀態恆為真；腳本返回 true 只是按鍵序列執行了。**教訓**：每個通道建立自己的假信號目錄，唯一可信的儀表是讀回的牆面內容。

### 案例五：通知驗證誤報（2026-11-20）
通知 ChatGPT 新規則後，探針只搜自己預想的確認句「收到，已了解這項新規則」、且只看牆上最後 8 段——對方實際回覆是「已收到並確認」＋逐條復述，被誤報為「無回應」。主人一眼看出「ChatGPT 之前不是都會回嗎」。**教訓**：①先搜自己訊息的獨有標記確認落窗，再讀其後回覆原文（措辭由對方定）；②驗證窗口要覆蓋全文，不是尾部片段；③誤報被糾正後，把教訓寫進技能筆記並向全體回報修正。

## 泛化規則

1. 「失敗 → 根因 → 泛化 → 沉澱」四步走完才算結案：每次誤判都要變成規則或坑位清單。
2. 教訓寫進技能筆記（只在相關任務時載入），而非通用記憶——避免污染無關任務的上下文。
3. 誠實邊界：中繼者主動承認誤報、更正結論，比被發起者抓包更有信任價值。
