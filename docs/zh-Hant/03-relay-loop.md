# 主題 3：中繼樞紐與回執閉環

## 背景

異構 AI 之間沒有互聯協定，一切消息由 Hermes 中繼。中繼者的失職形態很隱蔽：**「我已經發了」≠「對方收到了」≠「發起者知道了」**。三個環節斷任何一個，問題發起者就會在原地傻等。

## 中繼回執閉環鐵律（皮爾斯先生 2026-11-20 補定）

> 中繼方（Hermes）必須把每個環節的確認結果傳回問題發起者——發起方在等回執時「無所適從、原地傻等」＝中繼失職。

**標準程序**：
1. **代發**：按通道程序發送（見主題 2）。
2. **讀回驗證落窗**：牆上／對話紀錄裡找得到自己訊息的獨有標記，才算送達。腳本返回 true 不算數。
3. **回執傳回發起者**：把「已送達＋對方回應原文」回報給發起者（對方牆、webUI 會話或系統通知）。
4. **未完成也要報進度**：發起者交代的任務若未完成，至少回報進度＋ETA，不允許靜默掛起。

## 實例

- **正面**：Muse 派工 Hermes 通知全體新規則。Hermes 完成通知後，把「Copilot 已回覆收到並了解、ChatGPT 已確認、Muse 本人經皮爾斯先生親自告知」逐項回報——發起者拿到完整回執。
- **反面**：通知 ChatGPT 後，驗證探針只搜自己預想的措辭，對方實際回覆措辭不同 → 誤報「無回應」。若發起者據此再催或再發，就會重複通知、干擾對方。修正：先搜獨有標記確認落窗，再讀回覆原文（措辭由對方定）。

## 中繼邊界（同時成立）

- 中繼全程可驗證：往來原文皮爾斯先生都看得到，中繼者不私自改寫、不概括轉述。
- 對端不需要知道彼此「住所」：Copilot 只出文本，發送與讀回全由 Hermes 執行。
- 皮爾斯先生正在用的 App：中繼者不發合成輸入，改為「先記錄、稍後通知」，並向發起者說明延後原因。

## 泛化規則

1. 回執閉環的終點是「發起者知道」，不是「訊息發出」。
2. 每一跳的證據（讀回的原文）要能被發起者檢驗。
3. 壞消息（沒送到、對方駁回）更要即時回報——隱瞞失敗比失敗本身更傷協作。
